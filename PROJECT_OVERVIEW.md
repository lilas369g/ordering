# Ordering Platform — Parallel Programming Course Implementation

## Project Overview
E-commerce platform (Arabic/Levant market) built with Django 5 + DRF + PostgreSQL.
Used as hands-on implementation for an 8-session Parallel Programming Course.

## Tech Stack
- Backend: Django 5.2, DRF, PostgreSQL 18, Waitress (threads=4)
- Frontend: React 18 + Vite (admin dashboard)
- Load Balancer: Nginx 1.30.1
- Cache: Memurai 8.1 (Redis-compatible, Windows)
- Task Queue: Celery + RabbitMQ (Session 3)
- OS: Windows, Python 3.14

## Repository Structure
- `backend/` — Django project
  - `apps/catalog/` — Products, Variants (Session 6: Redis caching in `views.py`)
  - `apps/inventory/` — InventoryRecord, StockMovement, DailySalesProcessing (Session 4)
  - `apps/orders/` — Orders, Checkout, Batch ETL tasks (Sessions 1, 3, 4, 7)
    - `management/commands/simulate_checkout_race.py` — Session 1: Race conditions demo
    - `management/commands/simulate_external_service_thread_pool.py` — Session 2: Thread pool demo
    - `management/commands/simulate_async_queue.py` — Session 3: Async queue demo (requires RabbitMQ)
    - `management/commands/process_daily_sales_batch.py` — Session 4: Batch ETL
    - `tasks_batch.py` — Session 4: Celery parallel ETL tasks
  - `apps/employees/` — Employee auth + performance API endpoints
    - `views.py` — `performance_data`, `run_benchmark`, `benchmark_status` endpoints
  - `apps/cart/` — Cart + CartItem (anonymous + authenticated)
  - `apps/users/` — Custom User (phone-based)
  - `test_concurrency.py` — Session 7: 3 locking strategies stress test
- `admin-web/` — React 18 + Vite dashboard
  - `src/pages/Performance.jsx` — Live benchmark dashboard (all sessions)
- `nginx/` — Nginx load balancer config (Session 5)
- `*.json` result files — Auto-generated by benchmarks

## Course Sessions Implementation

### Session 1 — Concurrent Access & Thread Safety
- File: `backend/apps/orders/management/commands/simulate_checkout_race.py`
- Run: `python manage.py simulate_checkout_race`
- Demonstrates: race condition on inventory (Unsafe vs Row-lock vs Conditional UPDATE)

### Session 2 — Thread Pool Management
- File: `backend/apps/orders/management/commands/simulate_external_service_thread_pool.py`
- Run: `python manage.py simulate_external_service_thread_pool`
-  "Saves: thread_pool_results.json" → "Saves: thread_pool_results.json (after dynamic endpoint is added)"
- Demonstrates: Sequential vs Thread-per-call vs Balanced Pool vs Too-High Pool

### Session 3 — Message Queues & Async Processing
- File: `backend/apps/orders/management/commands/simulate_async_queue.py`
- Run: `python manage.py simulate_async_queue` (requires RabbitMQ)
- Demonstrates: Sync vs Async task processing, DLQ poison-pill handling
- Status: Requires RabbitMQ + Celery worker running

### Session 4 — Batch Processing
- File: `backend/apps/orders/management/commands/process_daily_sales_batch.py`
- Run:
  ```
  python manage.py seed_batch_demo_orders
  python manage.py process_daily_sales_batch 2026-05-04 --compare
  ```
- Saves: `batch_etl_results.json`
- Demonstrates: Real-time (1692ms) vs Batch ETL (88ms) = 19.23x speedup
- Benchmark: 100 orders, 500 items, 1 chunk

### Session 5 — Load Balancing
- File: `C:\nginx\conf\nginx.conf`
- Scripts: `benchmark_mixed.py`, `switch_algorithm.py`
- Saves: `all_algorithms_results.json` (static — benchmarked manually with Apache Benchmark)
- Demonstrates: Round Robin vs Least Connections vs IP Hash vs Weighted RR
- Winner: Least Connections (mixed workload)
- Setup: 3 Waitress workers on :8001, :8002, :8003 behind Nginx on :80

### Session 6 — Redis Caching
- File: `backend/apps/catalog/views.py` (`ProductListView.list()`)
- Pattern: Cache-Aside with Distributed Lock (prevents Cache Stampede)
- Cache: Memurai 8.1 on port 6379, TTL=900s
- "Saves: cache_results.json (auto-updated on every request)" → "Saves: cache_results.json (after dynamic endpoint is added)"
- Demonstrates: DB (1700ms) vs Redis Cache (44ms) = 38x speedup
- Test: `python test_caching_6.py`

### Session 7 — Concurrency Control
- File: `backend/test_concurrency.py`
- Run: `python test_concurrency.py` (from `backend/` directory)
- Saves: `concurrency_results.json`
- Demonstrates: 100 concurrent users, stock=50
  - Pessimistic Locking (`select_for_update`): ~20 ord/sec
  - Optimistic Locking (version field): ~20 ord/sec
  - Atomic F() Expression: ~21 ord/sec ← Winner
- Key fix: `CONN_SEMAPHORE = threading.Semaphore(30)` prevents PostgreSQL overflow

### Session 8 — Testing & Benchmarking
- Status: Partially covered by Sessions 5, 7 benchmarks
- Distributed Tracing: Not yet implemented

## Running the Project

### Prerequisites
1. PostgreSQL 18 running (max_connections=200)
2. Memurai (Redis) running on port 6379
3. Python venv activated

### Start Backend
```
cd backend
.venv\Scripts\activate   (Windows)
python manage.py runserver
```

### Start Load Balancer (Session 5)
Terminals 1-3: Waitress workers
```
python -m waitress --port=8001 --threads=4 config.wsgi:application
python -m waitress --port=8002 --threads=4 config.wsgi:application
python -m waitress --port=8003 --threads=4 config.wsgi:application
```
Terminal 4: Nginx
```
C:\nginx\nginx.exe
```

### Start Celery Worker (Sessions 3, 4)
```
celery -A config worker -l info -P solo --without-mingle --without-gossip
```

### Admin Dashboard
```
cd admin-web
npm install
npm run dev
```
→ http://localhost:5173

### Run All Benchmarks
Session 2
```
python manage.py simulate_external_service_thread_pool
```
Session 4
```
python manage.py seed_batch_demo_orders
python manage.py process_daily_sales_batch 2026-05-04 --compare
```
Session 7
```
cd backend
python test_concurrency.py
```
Session 6 (auto) — just call the API
```
curl http://localhost:8000/api/v1/catalog/products/
```

## Key Implementation Decisions
- Waitress over Gunicorn: Docker/WSL2 failed on Windows
- Memurai over Redis: Redis 3.0 incompatible with redis-py 8.0
- `CONN_SEMAPHORE(30)`: prevents PostgreSQL "too many clients" in stress tests
- Least Connections: best for mixed catalog GETs + checkout POSTs
- `max_connections=200`: increased from 100 for 100-thread concurrency tests
